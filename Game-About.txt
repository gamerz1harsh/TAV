GAME DESIGN AND ARCHITECTURE SKELETON
===================================

This file contains a skeleton framework for the game concept discussed so far.
It is intended to be expanded into a real implementation later.

------------------------------------------------------------
1. GAME CONCEPT SUMMARY
------------------------------------------------------------

Core Idea:
- The game is a long-form, choice-driven life simulation with an open world.
- The player creates a character and starts in a defined world.
- The story progresses year by year.
- Each year, the player faces four major main-event choices.
- Random events can happen at any time between those major events.
- These events change the world, the player’s relationships, and future choices.

Design Goal:
- Make the story feel dynamic, personal, and replayable.
- Avoid a linear job menu.
- Make careers, social status, and opportunities emerge from actions and relationships.

Optional Optimization Note:

- Alternative approach: start with one city and one era before expanding to a full open world.

------------------------------------------------------------
2. GAMEPLAY LOOP
------------------------------------------------------------

Loop Structure:
1. Create character
2. Start in a location
3. Explore the world
4. Visit locations and interact with NPCs
5. Trigger random encounters or events
6. Make choices
7. Update character state and world state
8. Advance to the next year
9. New main events appear
10. Repeat with new consequences

Suggested Flow:
- Player enters a location
- The system loads nearby NPCs, items, and events
- The player can talk, act, observe, or travel
- Outcomes change relationships, resources, skills, knowledge, prestige, and story flags
- The next year’s events are influenced by these changes

Optimization Note:
- Keep the loop as simple as possible at first: location -> choice -> consequence -> year progression.
- Alternative approach: add a “timeline” panel that summarizes year outcomes and unresolved opportunities.

------------------------------------------------------------
5. YEARLY SYSTEM
------------------------------------------------------------

Year Structure:
- Every year contains a phase of main events.
- The player may also experience random events during the year.
- Events can change what is possible next year.

Main Event System:
- Each year, four choices appear.
- These are the major decisions of the year.
- They can lead to:
  - career changes
  - social changes
  - political changes
  - personal growth
  - world events

Random Event System:
- Random events happen between the main events.
- These events may include:
  - meeting a friend
  - theft
  - helping someone
  - receiving an opportunity
  - being betrayed
  - discovering a clue
  - meeting a powerful person

Effect of Events:
- relationship changes
- resource changes
- skill changes
- reputation changes
- unlocks new paths
- changes future main events

Optional Optimization Note:
- Use a weighted event system so some events appear more often than others.
- Alternative approach: create event pools based on current year, location, and player state.

7. NPC SYSTEM
------------------------------------------------------------

NPC Design:
- NPCs are not static.
- They can appear, disappear, change their behavior, and affect the story.

NPC Fields:
- Name
- Role
- Age or life stage
- Personality
- Occupation or function
- Relationship level with player
- Trust level
- Reputation level
- Current location
- Current activity
- Beliefs or affiliations
- Memory of past interactions
- Importance to story

NPC Behavior Rules:
- Some NPCs are always present in a location.
- Others appear only under certain conditions.
- Some are only visible at certain times.
- Some appear based on relationships, reputation, or story flags.

Optional Optimization Note:
- Keep NPC templates simple and use procedural generation for minor details.
- Alternative approach: use a small set of archetypes and then customize them with variables.

------------------------------------------------------------
8. AUTONOMOUS NPC BEHAVIOR
------------------------------------------------------------

Concept:
- Not every NPC should be fully autonomous.
- Some should feel reactive, and others should feel more alive.

AT: Autonomous Thinking
- Stronger behavior layer
- NPCs with this layer can:
  - move around a location
  - talk to nearby NPCs
  - interact with the player
  - form friendships or rivalries
  - react to events
  - follow their own goals

PAT: Pseudo-Autonomous Thinking
- Lower-cost behavior layer
- NPCs with this layer can:
  - react when the player approaches
  - show mood changes
  - speak a short line
  - act based on simple rules
  - be background characters without full simulation

Behavior Logic:
- Relationship level affects behavior.
- Strong positive relation = friendly, supportive, helpful
- Neutral relation = normal, casual, indifferent
- Negative relation = avoidant, hostile, or suspicious

Closest-NPC Rule:
- The system can assign AT behavior to the NPC closest to the player in a location.
- Other nearby NPCs can receive PAT behavior.
- This creates a dynamic feeling without requiring full AI for every character.

Optional Optimization Note:
- Use a small number of active NPCs per location to reduce CPU and memory use.
- Alternative approach: switch between AT and PAT depending on distance, importance, or story relevance.

------------------------------------------------------------
10. CAREER AND OPPORTUNITY SYSTEM
------------------------------------------------------------

The game should not force a fixed job menu.
Instead, careers should emerge from the player’s actions.

Career Progression Principle:
- The player does not simply choose a profession.
- The player builds a path through skills, relationships, opportunities, reputation, and knowledge.

Examples:
- Political path
  - player meets activists or politicians
  - player forms ideology and support network
  - player joins a movement or party
  - player gains publicity
  - player may eventually run for office or become a leader

- Medical path
  - player studies medicine
  - player earns credentials or degrees
  - player meets mentors and professionals
  - player applies for positions
  - player attends interviews or assessments
  - player begins a medical career

- Engineering path
  - player builds skills and knowledge
  - player creates projects or portfolios
  - player gains recommendations
  - player applies to companies or labs
  - player receives opportunities

Opportunity System:
- Opportunities are generated based on:
  - skills
  - relationships
  - ideology
  - reputation
  - location
  - random events
  - education level

Optional Optimization Note:
- Keep career trees simple and use tags rather than complex branching logic at first.
- Alternative approach: use a rule-based opportunity generator instead of hand-authored career paths.

------------------------------------------------------------
11. DYNAMIC POLITICAL PATH EXAMPLE
------------------------------------------------------------

Example Design:
- The player meets a Democrat or political organizer.
- The player builds trust through conversations and shared actions.
- The player joins campaign events or community causes.

- The player gains followers or allies.

Optional Optimization Note:
- Use a simple ideology system first, such as moderate, liberal, conservative, populist, revolutionary, neutral.
- Alternative approach: use a custom ideology vector with multiple axes.

15. CARD SYSTEM
------------------------------------------------------------

Cards should be auto-generated for major world objects.

Card Types:
- Place cards
- NPC cards
- Item cards
- Event cards
- Opportunity cards
- Relationship cards
- Quest or story cards

Card Content:
- name
- short description
- icon or image
- tags
- current state
- relationship to player
- available actions
- related entities

Example:
- NPC card contains role, trust, current location, current mood, and available actions.
- Place card contains type, current occupants, safety level, and available interactions.
- Item card contains item type, condition, value, and use cases.

Dynamic Card Updates:
- Cards update when the player changes relations, gains skill, or triggers events.
- Cards should be regenerated from current state rather than being manually stored forever.

Optional Optimization Note:
- Use a shared card template and different data schemas for each card type.
- Alternative approach: keep cards lightweight and render them from a data object instead of a full UI component each time.

------------------------------------------------------------
16. DATA STORAGE PLAN
------------------------------------------------------------

The backend should store data in JSON and JSONL for simplicity and readability.

Suggested Files:
- world.json
  - shared world settings and rules
- player_state.json
  - player stats, resources, location, progress, flags
- npcs.json
  - NPC definitions and current state
- locations.json
  - location definitions, current population, active events
- items.json
  - item inventory and world items
- events.jsonl
  - append-only event log
- memories.jsonl
  - NPC and player memories
- logs.jsonl
  - debug and history log

Suggested Record Format:
- id
- type
- timestamp
- text
- tags
- linked_entities
- priority
- importance

Example Memory Record:
- id: mem_001
- type: memory
- text: “Alice trusted the player after helping at school.”
- tags: friendship, school, trust
- linked_entities: player, alice, school_event

Optional Optimization Note:
- Use a database later if the game grows large.
- Alternative approach: keep a hybrid system using JSON for small projects and SQLite/Postgres for scale.

------------------------------------------------------------
17. RETRIEVAL AND MEMORY SYSTEM
------------------------------------------------------------

The game needs a fast way to retrieve relevant memories, logs, and story context.

Recommended Approach:
- Store structured memory data in JSONL.
- Index text data using BM25.
- Retrieve the most relevant memories for the current scene.
- Use those results as context for dialogue, NPC behavior, or story generation.

Retrieval Flow:
1. Build a query from the current context
2. Search the memory index
3. Retrieve top results
4. Rank by recency, relevance, and importance
5. Feed a limited set into the model or logic engine

Suggested Retrieval Fields:
- text
- tags
- linked entities
- timestamp
- importance
- memory owner

Optional Optimization Note:
- Do not retrieve too much context at once.
- Alternative approach: use a two-stage retrieval system: BM25 first, then reranking by importance.

------------------------------------------------------------
18. LOCAL MODEL AND PERFORMANCE PLAN
------------------------------------------------------------

The game should not depend entirely on a heavy local model.
The model should be used carefully because the hardware is limited.

Hardware Context:
- Laptop GPU: 5050 class
- RAM: 16 GB
- Model target: Gemma 4 8B

Recommended Strategy:
- Use the local model for high-value moments only.
- Use rule-based logic for everyday systems.

Suggested Usage Tiers:
- Tier 1: Rules and heuristics
  - relationship changes
  - simple encounter resolution
  - NPC movement
  - location state updates

- Tier 2: Small local generation
  - dialogue lines
  - short event descriptions
  - NPC reactions
  - simple conversational responses

- Tier 3: Larger or more expensive generation
  - major story scenes
  - long branching dialogue
  - core narrative summaries

Performance Rules:
- Keep prompts short
- Keep context small
- Use quantized models when possible
- Avoid generating long responses repeatedly
- Cache common outputs

Optional Optimization Note:
- Use a smaller model for routine interactions and reserve larger models for meaningful narrative moments.
- Alternative approach: use a remote model for story events and a local model for lightweight interactions.

Data Layer:

20. IMPLEMENTATION ROADMAP
------------------------------------------------------------

Phase 1: Foundation
- Create basic world and player state system
- Create locations and NPC templates
- Create simple yearly progression
- Create basic event and relationship systems

Phase 2: Interaction Layer
- Add locations and exploration
- Add NPC interactions
- Add event cards and dynamic UI cards
- Add simple memory logging

Phase 3: Career and Opportunity System
- Add skill and education progression
- Add application and interview flow
- Add ideological and political opportunity logic

Phase 4: World Customization
- Add genre, era, setting, and technology parameters
- Add adaptive menu system
- Add world-generation templates

Phase 5: Memory and Retrieval
- Add JSONL logs and memory storage
- Add BM25 indexing
- Add retrieval for relevant context

Phase 6: AI Integration
- Add local model support for dialogue and event generation
- Add rule-based fallback system
- Add performance limits and prompt budgeting

Optional Optimization Note:
- Build in vertical slices: one location, one career path, one event type, and one NPC type first.
- Alternative approach: build a text-based prototype before a full visual app.

------------------------------------------------------------
21. RECOMMENDED STARTING MVP
------------------------------------------------------------

The best first version should be small and focused.

Suggested MVP:
- One player character
- One city or town
- Three core locations
- Five to ten NPCs
- One yearly progression loop
- One political path and one professional path
- Basic event cards
- Basic memory and logs
- Basic BM25 retrieval
- Rule-based NPC behavior

This MVP is enough to test the design without overwhelming the project.

Optional Optimization Note:
- Keep the first build to one era and one genre.
- Alternative approach: build the modern-city version first because it supports richer UI and more obvious career systems.

------------------------------------------------------------
22. FINAL DESIGN PRINCIPLE
------------------------------------------------------------

The project should be built around this idea:
- The world is dynamic.
- The player shapes the story through actions.
- NPCs and locations react to the player.
- Careers emerge from life choices rather than fixed menu options.
- AI should enhance the experience, not replace the core simulation.

This is the foundation for turning the concept into a working app.
