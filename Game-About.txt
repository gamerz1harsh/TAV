RIVERTON
GAME DESIGN AND ARCHITECTURE
============================

This document is the current design reference for Riverton. It replaces the
earlier broad open-world skeleton with a manageable desktop-first plan.

The project is built in layers:
- a deterministic life-simulation core
- a native desktop interface
- specialized systems for event selection, memory, NPC logic, and narration

The game will not rely on a single LLM to control everything. Rules remain
authoritative; models are used only where they add variety or natural language.

---------------------------------------------------------------------
1. PRODUCT VISION
---------------------------------------------------------------------

Riverton is a choice-driven life simulation. The player spends a year in a
modern neighborhood, builds relationships, makes tradeoffs, and sees their
future emerge from actions rather than from a fixed career menu.

Design goals:
- Choices must have visible and lasting consequences.
- Different origins, relationships, and actions must create different runs.
- The game must remain fast and predictable on modest hardware.
- Story text should feel personal without allowing generated text to break
  rules, state, or balance.

---------------------------------------------------------------------
2. CURRENT VERTICAL SLICE (V1 / V2)
---------------------------------------------------------------------

The current playable scope is one year in Riverton.

World:
- Modern neighborhood
- Apartment
- Juniper Cafe
- Community College

NPCs:
- Maya Ortiz, roommate
- Leo Chen, classmate
- Priya Shah, cafe manager
- Dr. Ellis Reed, career mentor
- Sam Walker, community organizer
- Nora Blake, local rival

Player stats:
- Energy
- Money
- Skill
- Reputation

Relationship stats per NPC:
- Affinity
- Trust

Replayability systems already defined:
- Four origins with different starting advantages and relationships
- Four seasonal main decisions
- Weighted random events with eligibility conditions
- Four primary ending paths
- Three actions per season
- JSON local save state

Current implementation note:
- The playable prototype is a PySide6 native desktop application.
- The previous browser prototype is retained only as development history and is
  no longer the primary way to run the game.

---------------------------------------------------------------------
3. CORE GAMEPLAY LOOP
---------------------------------------------------------------------

1. Start a new life and choose an origin.
2. Begin a season with three actions.
3. Travel freely between locations.
4. Spend actions talking, helping, or working with NPCs.
5. Resolve any random event that appears.
6. Use all actions, then make the season's main decision.
7. Apply consequences to stats, relationships, flags, memories, and paths.
8. Restore three actions and advance to the next season.
9. At year end, calculate an outcome from the player's full state.

Travel is free. NPC interactions cost one action. The seasonal limit prevents
stat farming and creates meaningful tradeoffs.

---------------------------------------------------------------------
4. ORIGINS
---------------------------------------------------------------------

Each origin changes starting stats, initial relationships, and likely early
opportunities.

- Scholarship Student
  - Higher Skill, lower Money
  - Knows Leo

- Cafe Worker
  - Higher Money, lower Energy
  - Knows Priya

- Local Resident
  - Higher Reputation
  - Knows Sam

- New Arrival
  - Higher Energy
  - No established connection

Origins must affect gameplay rather than merely changing flavor text.

---------------------------------------------------------------------
5. CAREER AND ENDING PATHS
---------------------------------------------------------------------

Paths are unlocked by combinations of flags, stats, and NPC trust. They are
not selected directly from a job menu.

Initial ending paths:
- Professional path: study, portfolio, application, interview, Skill, and
  Dr. Ellis's trust lead to a trainee offer.
- Community path: community work, campaign progress, public action,
  leadership, Reputation, and Sam's trust lead to an organizer role.
- Cafe path: dependable work, Priya's trust, and financial stability lead to
  greater responsibility at the cafe.
- Independent path: Skill and savings lead to a small self-directed project.
- Foundation ending: a valid outcome for an unfinished or mixed first year.

---------------------------------------------------------------------
6. NATIVE DESKTOP DIRECTION
---------------------------------------------------------------------

Target platform:
- Windows desktop first

Recommended toolkit:
- Python + PySide6 / Qt Widgets

Reason:
- Keeps the existing Python simulation logic.
- Provides a real native desktop window with no browser or web server.
- Supports a card-based interface, scrollable journal, local files, and later
  model integration.

Native UI screens:
- New-game and origin selection screen
- Main seasonal dashboard
- Location and NPC panels
- Fixed-height, scrollable journal
- Main-event and random-event panels
- Character and relationship view
- End-of-year outcome screen

Migration rule:
- Move the game rules out of the current web application before rebuilding
  the interface.
- The rules engine must run without a UI, web server, or LLM.

Suggested native project layout:

    riverton/
      game_engine/
        state.py
        events.py
        relationships.py
        event_director.py
        storage.py
      desktop/
        main.py
        main_window.py
        views/
      data/
        save_state.json
        events.jsonl
        memories.jsonl

---------------------------------------------------------------------
7. AUTHORITATIVE SIMULATION CORE
---------------------------------------------------------------------

The simulation core is the single source of truth. It owns:
- player state
- stats and resources
- relationships
- actions remaining
- seasonal progression
- eligibility rules
- event effects
- unlocks and endings
- save/load operations

Generated prose must never directly change these values. Every state change
must be represented as structured data and applied by the simulation core.

Example effect object:

    {
      "money": 2,
      "energy": -1,
      "trust": {"priya": 1},
      "flags": {"cafe_shift": true}
    }

---------------------------------------------------------------------
8. EVENT DIRECTOR
---------------------------------------------------------------------

The Event Director is a specialized system that chooses which eligible event
is most useful and interesting for the current player state.

It does NOT create arbitrary events or change the game state. It selects from
events supplied by the rules engine.

Pipeline:

    Current game state
          |
          v
    Rules filter: eligible event candidates
          |
          v
    Event Director: score and rank candidates
          |
          v
    Rules engine: activate selected event
          |
          v
    Narrative model: describe the selected event

Candidate event data includes:
- id
- title
- structured choices and effects
- location requirement
- required stats
- required relationship values
- required or forbidden flags
- weight
- tags
- cooldown or recent-use rules

Example:

    {
      "id": "extra_shift",
      "requires": {
        "location": "cafe",
        "npc": {"priya": {"trust": 1}}
      },
      "weight": 3,
      "tags": ["cafe", "money", "priya"]
    }

---------------------------------------------------------------------
9. EVENT DIRECTOR EVOLUTION
---------------------------------------------------------------------

V1 Event Director: deterministic scoring

The first version uses a transparent score rather than ML:

    score =
        relevance_to_player * 3
        + relationship_tension * 2
        + path_progress * 2
        + novelty * 2
        - recently_seen_penalty * 4

This should favor events that:
- relate to active player paths
- react to high or low NPC relationships
- advance unfinished story threads
- introduce variety
- avoid recent repetition

V2 Event Director: learned ranking

Log structured gameplay data:
- candidate events
- selected event
- player state features
- player choice
- follow-up outcome
- event frequency

Use this data for a small contextual bandit or ranking model. This is better
than early RL because it can learn useful event preferences from short,
individual event decisions.

V3 Event Director: reinforcement learning research

Only consider RL after there are many test runs and a defined reward function.
Possible reward components:
- narrative variety
- meaningful player agency
- balanced difficulty
- completion of long-term paths
- avoidance of repetitive or contradictory events

Never allow an RL policy to bypass hard eligibility, safety, or balance rules.

---------------------------------------------------------------------
10. ORCHESTRATOR AGENT
---------------------------------------------------------------------

The game needs a coordinator, called the Game Orchestrator. At first this is
deterministic Python code, not an uncontrolled autonomous LLM agent.

It coordinates specialized systems:

    Native UI
       |
       v
    Game Orchestrator
       |- Simulation Core
       |- Memory Retrieval
       |- Event Director
       |- NPC Logic
       `- Narrative LLM

Orchestrator responsibilities:
- determine which system runs next
- prepare only the context that system needs
- enforce time, token, and memory budgets
- validate structured responses
- record logs and memories
- call the simulation core to apply allowed changes

The Orchestrator must not permit generated text to directly write a save file.

---------------------------------------------------------------------
11. LOCAL LLM: NARRATION ONLY
---------------------------------------------------------------------

The local LLM improves presentation, not simulation logic.

Appropriate tasks:
- short event descriptions
- NPC dialogue lines
- mood-sensitive reactions
- concise season summaries
- rewrite structured event outcomes in a natural style

The local LLM receives:
- selected event id and description
- allowed factual context
- a small selection of relevant memories
- tone and length constraints

The local LLM returns:
- text only, or a tightly validated structured response

It must not:
- invent an event outcome
- change stats, trust, money, or flags
- introduce NPCs or facts that do not exist in state
- write long responses during ordinary actions

Use rules-based fallback text whenever a local model is unavailable or slow.

---------------------------------------------------------------------
12. MEMORY AND RETRIEVAL
---------------------------------------------------------------------

Memory is stored as structured JSONL records. Each memory includes:
- id
- timestamp / season
- text
- tags
- linked entities
- importance
- owner (player or NPC)

Example:

    {
      "id": "mem_012",
      "season": "Summer",
      "text": "The player returned a wallet to Priya.",
      "tags": ["cafe", "trust", "priya"],
      "linked_entities": ["player", "priya"],
      "importance": 3
    }

Retrieval order:
1. exact entity and tag match
2. recency and importance ranking
3. later: BM25 text retrieval
4. later: reranking if required

Only a small set of relevant memories should be passed to the narrative model.

---------------------------------------------------------------------
13. NPC LOGIC
---------------------------------------------------------------------

NPC behavior remains mostly rule-driven.

NPC state includes:
- role and location
- affinity and trust
- availability
- current mood or status
- simple goals
- memory tags
- story importance

Relationship rules:
- High trust unlocks invitations, opportunities, and support.
- Low trust can close paths, create tension, or enable conflict events.
- NPC memory gives later events continuity.

The narrative model may describe NPC behavior, but NPC availability and
consequences are decided by the simulation core.

---------------------------------------------------------------------
14. DATA AND LOGGING
---------------------------------------------------------------------

Local data files:
- save_state.json: current game state
- events.jsonl: activated events and choices
- memories.jsonl: structured player and NPC memories
- director_log.jsonl: candidates, scores, and selected events
- model_log.jsonl: optional prompt/result timing and fallback use

Logs are required for debugging balance, tracking repetition, and training a
future event-ranking model.

---------------------------------------------------------------------
15. PERFORMANCE PRINCIPLES
---------------------------------------------------------------------

- Prefer rules and small structured objects over model calls.
- Generate prose only for meaningful events, not every button press.
- Keep model prompts short and grounded in retrieved context.
- Cache or reuse common template text.
- Run one local model task at a time on modest hardware.
- Always have deterministic fallback narration.

16. DEVELOPMENT ROADMAP
---------------------------------------------------------------------

Completed:
- V1: one-year playable vertical slice
- V2: origins, weighted random events, path hints, endings, and replayability
- V2.1: seasonal three-action budget and fixed scrollable journal

Completed: Native migration
- Game rules are extracted into a UI-independent engine.
- A PySide6 desktop shell provides the origin screen and seasonal dashboard.
- The native app preserves the JSON save format.

Next:
- V2.2: conditional seasonal main events based on origins, stats, trust, and
  active paths
- V2.3: stronger NPC relationship consequences
- V2.4: Event Director v1 deterministic scoring and director logs
- V2.5: structured memory storage and retrieval
- V2.6: local LLM narration with rules-based fallback

Future:
- V3: multiple years, longer careers, changing NPC lives, and expanded world
- V4: learned event ranking from logged playthroughs
- V5: evaluate RL only after sufficient data and stable reward metrics

---------------------------------------------------------------------
17. FINAL PRINCIPLE
---------------------------------------------------------------------

Riverton is a simulation first and an AI experience second.

Rules create fair consequences. The Event Director creates variety. Memory
creates continuity. The local LLM creates voice. The native interface makes
the experience feel like a real desktop game.
